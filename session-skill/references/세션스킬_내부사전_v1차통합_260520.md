## 패턴 1. Stage·HITL 도구 분담

> **영역**: 1. AI 역할 축소 · **빈도**: ★★★ · **흡수**: #7 Stage 1·2·3 도구 분담 + #11 AI 역할 좁히기 + #33 휴먼인더루프

### 기본 분류
- 영역: 1. AI 역할 축소
- 패턴: 1. Stage·HITL 도구 분담
- 실행 양식: (3 갈래) Stage별 처리 영역 분담 / AI 역할 축소 / 사람 개입 지점 설계

### 한 줄 기준

AI가 통째로 맡고 있던 처리 영역에서 룰·LLM·사람 단계나 역할을 분리하지 않으면 over-fit·비결정성·신뢰 저하가 커질 때 적용한다.

### 적용 신호

**공통**
- AI가 데이터를 통째로 읽고 해석·요약·판단·생성까지 맡고 있다.
- 토큰·시간이 과도하거나 결과가 매번 다르게 나온다.

**Stage 분담 (#7)**
- 원본과 정답본이 있고, 사전·정규식·Few-shot·LLM pass 후보가 섞여 있다.
- 매번 같은 결과가 나야 하는 영역과 문맥 판단 영역이 함께 있다.
- 강의별 특수 용어·검수자 스타일처럼 사람이 남아야 할 영역이 있다.

**AI 역할 좁히기 (#11)**
- 실제로 필요한 것은 전체 해석이 아니라 특정 셀·항목의 라벨링이다.
- 코드로 격자 생성·렌더·검증을 강제할 수 있다.

**HITL (#33)**
- AI가 만들거나 점수화한 후보 목록이 있고, LD가 선택해야 할 기준이 있다.
- 사람이 한 번 선택하면 뒤 단계는 자동화할 수 있다.

### 비적용 신호

**Stage 분담 (#7)**
- 원본과 정답본 비교 자료가 없어 단계 분담 잣대를 잡을 수 없다
- 모든 처리가 단순 고정 변환이라 LLM·사람 검수 단계가 필요 X
- 룰·LLM·사람 검수 영역을 나눌 만큼 작업 구조가 복잡하지 않다
- 사람 검수 영역까지 자동화해야 한다는 전제가 이미 고정됨

**AI 역할 좁히기 (#11)**
- 사용자가 원하는 가치가 전체 종합 판단 자체에 있어 좁히면 안 됨
- LLM이 맡은 역할이 이미 라벨링·증거 압축처럼 좁다
- 문제의 핵심이 *느린 LLM*이 아니라 정량 계산 재현성 (코드·LLM 분리 패턴 7에 가까움)
- 역할을 좁히면 사용자가 원하는 전체 감각을 잃게 되는 영역

**HITL (#33)**
- 사람 개입 없이도 선택 기준이 명확하고 안전한 영역
- LD가 선택해야 할 기준이나 후보 목록 자체가 없다
- 사람 개입 자리가 너무 많아 자동화 효과가 사라질 위험
- 사람 개입 이후 이어지는 자동화 단계가 없어 HITL이 의미 없음

### 필요한 입력값

**공통**
- 기존 LLM 전담 흐름 / 처리 후보 / 사람 판단 영역

**Stage 분담 (#7)**: 원본과 정답본 / 사전·정규식·Few-shot·LLM 판단 후보 / 사람 최종 판단 영역
**AI 역할 좁히기 (#11)**: 반복되는 판단 단위 / 코드로 강제할 수 있는 구조 / LLM 좁은 역할 후보
**HITL (#33)**: AI 후보 목록·점수 결과 / LD 선택 기준 / 선택 후 자동화 단계 / 선택 근거 양식

### 판단 기준

- 매번 같은 결과가 나야 하면 Stage 1 사전·정규식 / 문맥 판단이면 Stage 2 LLM / 강의별 스타일·구두 판단이면 Stage 3 사람.
- LLM이 전체를 맡으면 토큰·시간·재현성 문제가 커진다.
- 사람 개입 자리는 자동화 효과를 깎지 않는 범위에서만 둔다.

### 추천 액션

- 실행 시점: AI 전담 흐름이 느리거나 결과가 흔들린다고 확인된 직후 / AI 후보·점수 결과 중 LD 선택 지점이 보일 때
- 실행 주체: 세션 담당자와 LD
- 액션 내용:
  - **Stage 분담**: 각 후보를 Stage 1(사전·정규식) / Stage 2(Few-shot·LLM) / Stage 3(사람 검수) / 보류로 나눔. Stage 1 항목은 FP=0 확인 기준 붙임
  - **AI 역할 좁히기**: 기존 LLM 작업을 라벨링·증거 압축 같은 좁은 역할로 다시 적고, 데이터 수집·격자 생성·렌더·검증은 코드 역할로 옮김
  - **HITL**: 사람 개입 위치·LD 선택 기준·선택 후 자동화 단계·선택 로그 양식 정함
- 완료 기준:
  - **Stage 분담**: 모든 후보가 Stage 1(사전·정규식) / Stage 2(Few-shot·LLM pass) / Stage 3(사람 검수) / 보류 중 하나로 배정되고, Stage 1 항목은 FP=0 기준으로 확인 가능한 점검 기준이 붙는다
  - **AI 역할 좁히기**: LLM 역할 정의(라벨링·증거 압축 등)·코드 역할 정의(데이터 수집·격자 생성·렌더·검증)·LLM 금지 룰이 분리되어 문서화된다
  - **HITL**: 사람 개입 위치·LD 선택 기준·후보 목록·선택 후 자동화 단계·선택 로그 양식이 정리된다

### 주의사항

- 오분류 위험: 룰 catch rate만 높이면 FP가 생겨 실무 신뢰 떨어짐 / LLM을 너무 좁히면 사용자가 원하는 전체 감각 잃음 / 사람 개입 자리가 너무 많으면 자동화 효과 사라짐
- 헷갈리는 패턴: 코드·LLM 분리(패턴 7) — Stage·HITL은 룰·LLM·사람 단계 분담이고, 코드·LLM 분리는 정량 계산과 LLM 해석의 역할 분리
- 쓰면 안 되는 조건: 단발 케이스를 일반 룰로 넣으려는 경우 / 전체 종합 판단이 도구의 핵심 가치인 경우 / LD 선택 기준이나 후보 목록이 없는 경우

### 대표 사례

- **Stage 분담**: 손승완 자막교정에서 사전·정규식·Few-shot·LLM pass를 분리. v8에서 룰 범위 96% 잡았고, 남은 20~25%는 LLM, 강의 특수 용어·쉼표 스타일은 검수자 영역으로 남김
- **AI 역할 좁히기**: 이현진 운영일지 — 해석형에서 누락 감지형으로 전환. AI는 활성 교육×체크포인트 셀에 5분류 라벨만 붙이는 좁은 역할
- **HITL**: 이수빈 커리큘럼 자동화 — 스코어링 뒤 LD가 직접 task 선택하는 자리 유지

### 정보 부족 시 확인 질문

## 패턴 2. 반복 운영 좁힘

> **영역**: 1. AI 역할 축소 · **빈도**: ★★★ · **흡수**: #12 셀 매트릭스×Window + #17 액티브 게이트

### 기본 분류
- 영역: 1. AI 역할 축소
- 패턴: 2. 반복 운영 좁힘
- 실행 양식: (2 갈래) 대상×점검항목×시점 격자화 / active 대상 게이트 설정

### 한 줄 기준

반복 운영 업무에서 *전체*가 아니라 *오늘 봐야 할 대상·시점*만 좁혀야 운영자와 AI 부담을 동시에 줄일 수 있을 때 적용한다.

### 적용 신호

**공통**
- 교육·딜·고객·프로젝트처럼 반복 점검 대상이 있다.
- 전체 항목을 다 보면 너무 많고, 비용이 높다.
- 운영자는 오늘 챙길 것만 알고 싶다.

**셀 매트릭스×Window (#12)**: 점검 항목별 자연 주기·도래 시점이 있다 / 증거 데이터 소스가 항목별로 나뉘어 있다
**액티브 게이트 (#17)**: active 조건과 비active 조건을 정할 수 있다 / 사용자가 예외를 지정해 강제 승격할 수 있어야 한다

### 비적용 신호

**셀 매트릭스×Window (#12)**
- 점검 대상별 자연 주기·도래 시점이 없거나 모두 동일하다
- 점검 항목과 증거 데이터 소스가 1:1로 분리되지 않는다
- 대상 자체를 좁히는 영역이 핵심 (액티브 게이트 갈래에 가까움)
- 체크포인트·window 잣대가 LD마다 너무 달라 표준화 어려움

**액티브 게이트 (#17)**
- 모든 대상이 지금 판단 대상이고 *대상 자체* 좁힐 잣대가 없다
- active와 비active 조건을 명확히 분리할 수 없다
- 시점 분기가 본질인 영역 (셀 매트릭스 갈래에 가까움)
- 사용자가 강제 승격할 수 있는 입구를 줄 수 없는 구조

### 필요한 입력값

**공통**: 대상 목록 / 점검 또는 점수 산출 기준 / 사용자 강제 예외 입력
**셀 매트릭스×Window**: 점검 항목 목록 / 항목별 도래 시점 / 증거 데이터 소스 / 결과물 구역
**액티브 게이트**: active 조건 / 비active 조건 / 점수 산출 대상 기준

### 판단 기준

- 전체 데이터를 처리하면 비용이 높고 운영자가 다 못 본다.
- 항목별 자연 주기가 있으면 window로 좁히고, active/비active를 나눌 수 있으면 게이트로 좁힌다.
- 두 양식 모두 *중요한 일이 빠지는 위험* 검토 + 사용자 예외 승격 입구가 필요하다.

### 추천 액션

- 실행 시점: 반복 운영 업무에서 확인 대상·점수 산출 대상이 너무 많아진 직후
- 실행 주체: 세션 담당자와 LD
- 액션 내용:
  - **셀 매트릭스×Window**: 대상×점검항목 격자 만들고 각 항목에 도래 시점 window 붙임. 오늘 window에 걸린 셀만 뽑아 결과물 구역으로 분류
  - **액티브 게이트**: active 조건·비active 트랙·강제 승격 규칙 정함. active 대상에만 점수 산출 적용, 사용자 예외 입력 남김
- 완료 기준:
  - **셀 매트릭스×Window**: 대상×점검항목 격자·window 규칙·오늘 도래 셀 목록·결과물 구역이 정리된다
  - **액티브 게이트**: active 조건표·비active 트랙·강제 승격 규칙·active 대상 점수 산출 범위가 정리된다

### 주의사항

- 오분류 위험: window가 잘못되면 중요한 일이 안 보임 / active 조건이 너무 좁으면 중요한 대상 빠짐
- 헷갈리는 패턴: 두 갈래끼리 — 셀 매트릭스×Window는 *오늘 볼 시점* 좁힘, 액티브 게이트는 *판단 대상 자체* 좁힘. AI 역할 좁히기(패턴 1)와도 헷갈림 — 이쪽은 LLM 작업 범위 좁힘이 아니라 *처리 대상* 좁힘
- 쓰면 안 되는 조건: 항목별 주기·도래 시점 합의 X / 사용자 판단 우선 원칙 없이 자동 제외하는 경우

### 대표 사례

### 주의사항

- 헷갈리는 패턴: 코드·LLM 분리(패턴 7) — Core/Shell은 사람 판단과 AI 구현 경계, 코드·LLM 분리는 정량 계산과 LLM 해석 경계
- 쓰면 안 되는 조건: LD가 정해야 할 판단이 비어있는데 AI 구현부터 시키는 경우

## 패턴 7. 결정론 계산 코드화

> **영역**: 2. 코드·LLM 분리 · **빈도**: ★★ · **흡수**: #1 코드/LLM 분리

- 패턴: 7. 결정론 계산 코드화
- 실행 양식: 코드/LLM 분리 진단

### 한 줄 기준

정량 계산·집계·비율·티어 판정처럼 같은 입력이면 항상 같은 출력이 나와야 하는 영역이 LLM에 맡겨져 있으면 적용한다.

### 적용 신호

- 평균·비율·응답자 수·점수·티어처럼 실행마다 달라지면 안 되는 값이 있다.
- 현재 LLM이 산술 계산이나 집계를 직접 하고 있다.
- 같은 raw를 두 번 실행했을 때 수치가 흔들릴 위험이 있다.
- 결과물 안에 정량 계산 결과와 LLM 해석이 섞여 있어 검증하기 어렵다.
- 코드로 고정할 영역과 LLM이 맡아야 할 문맥 판단 영역을 나눌 수 있다.

### 비적용 신호

- 정량 계산·집계·비율·티어 판정처럼 고정 출력이 필요한 항목이 없다.
- 업무의 핵심이 전부 문맥 해석·원문 요약·정성 판단에 가깝다.
- 이미 정량 계산은 코드로 분리되어 있고 문제는 결과 전달 방식이나 수신자별 액션 설계에 있다.
- 계산 규칙 자체가 아직 정리되지 않아 코드와 LLM 역할을 나누기 전에 형식지 명시화가 먼저 필요하다.

### 필요한 입력값

- raw CSV·시트·DB·설문 응답·딜 데이터처럼 정량 계산 가능한 원천 데이터
- 기존 LLM 프롬프트 또는 `SKILL.md`
- 사람이 기대하는 수치 산출 규칙
- 현재 결과물에서 정량 계산 항목 목록
- 현재 결과물에서 LLM 해석 항목 목록

### 판단 기준

- 평균·비율·응답자 수·스코어·티어 같은 값이 실행마다 달라지면 안 된다.
- LLM이 산술·집계를 직접 하고 있으면 위험 신호다.
- LLM은 정성 분류·원문 기반 해석·액션 제안에 남기는 것이 맞다.
- "LLM 추론이 결정론을 능가하면 안 됨"이 핵심 원칙이다.

### 추천 액션

- 실행 시점: 구현 전 진단 단계
- 실행 주체: 세션 담당자 또는 LD
- 액션 내용: 현재 프롬프트나 `SKILL.md`에서 정량 계산 영역과 LLM 판단 영역을 표로 나눔. 평균·비율·응답자 수·점수·티어 같은 코드 담당 항목과 원문 분류·개선점 해석·액션 제안 같은 LLM 담당 항목 분리
- 완료 기준: 모든 처리 항목이 코드 담당 또는 LLM 담당 중 하나로 배정되고, 정량 항목에는 같은 raw 2회 실행 시 같은 수치가 나와야 한다는 확인 기준 붙음

### 주의사항

- 오분류 위험: 정성 분류까지 억지로 코드화하면 도구가 경직됨
- 헷갈리는 패턴: Stage·HITL 도구 분담(패턴 1) — 코드·LLM 분리는 정량 계산과 LLM 해석 역할 분리, Stage·HITL은 룰·LLM·사람 검수 단계 분담
- 쓰면 안 되는 조건: 코드로 계산한 값을 LLM이 다시 수정하게 두면 분리 효과 사라짐
- 추가 주의: 수치 계산은 코드 출력 그대로 반영·LLM에는 해석만 맡김

### 대표 사례

- 안유진B: 만족도 분석 v1에서 LLM이 평균·긍정 비율까지 처리해 같은 raw를 두 번 돌려도 점수가 미세하게 달라짐. v2에서 `calculateScale5`·`calculateBipolar`·`calculateSelection`·`calculatePercentage` 같은 계산 함수를 코드로 옮기고, 불만·개선 분류는 LLM에 남김

## 패턴 8. LD 입력값 비교 검증

### 한 줄 기준

LLM이 추론한 결과를 LD가 직접 입력한 판단값과 비교할 수 있을 때 적용한다.

### 적용 신호

- LD가 직접 입력한 성사 가능성·상태·중요도 같은 값이 있다.
- LLM 추론 결과와 비교할 수 있다.
- LD 입력값이 충분히 채워져 있다.
- LLM 판단이 비결정적일 가능성이 있다.
- LD 직관이 현장 grounding으로 기능할 수 있다.

### 비적용 신호

- LD가 직접 입력한 판단값이 없다.
- LD 값 채움률이 낮아 비교 기준으로 쓰기 어렵다.
- LD 값 자체가 절대 진실이라고 보기 어렵고 보정 기준도 없다.
- 비교할 LLM 추론 결과가 없다.

### 필요한 입력값

- LD가 직접 입력한 값(성사 가능성·상태·중요도 등) / LLM 추론 결과 / 비교 기준 / 채움률 / 불일치 처리 기준

### 판단 기준

- LD 입력값이 모든 대상에 충분히 채워져 있다.
- LLM 판단이 비결정적일 가능성이 있다.
- LD 직관이 현장 grounding으로 기능할 수 있다.
- LD 값도 틀릴 수 있으므로 절대 진실이 아니라 비교 기준이다.

### 추천 액션

- 실행 시점: LLM 판단 결과와 비교 가능한 LD 입력값이 확인된 후
- 실행 주체: 세션 담당자 또는 AI
- 액션 내용: LD 값과 LLM 값을 대상별로 나란히 놓고 불일치 목록 만듦. 채움률 먼저 확인하고, 불일치 항목에서 LLM 판단 보정 규칙 찾음
- 완료 기준: LD 값 vs LLM 값 비교표·불일치 목록·LLM 판단 보정 규칙 후보 정리

### 주의사항

- 오분류 위험: LD 값을 절대 진실로 보면 나중에 무효화될 수 있음
- 헷갈리는 패턴: DIKW 정보화(패턴 18) — Grounding은 이미 있는 LD 판단값과 LLM 결과를 비교, DIKW는 raw를 판단 정보로 바꿈
- 쓰면 안 되는 조건: 채움률 확인 없이 LD 값을 anchor로 쓰는 경우
- 추가 주의: LD 값도 틀릴 수 있음·절대 진실이 아니라 비교 기준

### 대표 사례

## 패턴 9. 학습→구현→진화 3단계

> **영역**: 3. LD 자립 빌더 · **빈도**: ★★ · **흡수**: #3 체크리스트+프롬프트 + #24 자력 빌더 3단계 + #30 작은 루틴 직접 AX

### 기본 분류
- 영역: 3. LD 자립 빌더
- 패턴: 9. 학습→구현→진화 3단계
- 실행 양식: (3 갈래) 체크리스트+프롬프트 실행 / 자력 빌더 단계 전환 / 작은 루틴 AX 설계

### 한 줄 기준

LD가 도구 사용자에서 도구를 직접 진화시키는 사람으로 넘어가야 할 때 적용한다.

### 적용 신호

**공통**
- 한 번 만들어주는 것으로 끝나면 확산이 안 된다.
- LD가 AI에게 좋은 질문·판단을 주는 법을 배워야 한다.
- 코치가 점점 뒤로 빠져야 한다.

**체크리스트+프롬프트 (#3)**: LD가 자기 Claude에서 단계별로 직접 실행해야 함 / 진단·처방·구현·검증·효율 측정·다음 액션을 단계별로 나눌 수 있음
**자력 빌더 단계 전환 (#24)**: LD가 직접 판단할 diff·룰·검증 과제가 있음 / "명확해서 혼자 해볼 수 있을 것 같다" 같은 자력 신호
**작은 루틴 AX (#30)**: 30분~1시간짜리 작은 반복 업무 / AX팀이 매번 대신 만들어줄 수 없음 / LD가 작은 자동화를 계속 직접 만들 수 있어야 함

### 비적용 신호

**체크리스트+프롬프트 실행 (#3)**
- LD가 직접 실행·학습할 필요 없이 세션 담당자가 일회성 산출물만 만들면 됨
- 작업의 핵심이 프롬프트 실행이 아니라 데이터 구조·계산 로직·권한 문제 해결에 있다
- 단계별로 나눌 만큼 업무가 복잡하지 않고 단일 질문으로 충분
- LD 자립보다 빠른 대리 구현이 더 중요한 긴급 상황

**자력 빌더 단계 전환 (#24)**
- LD가 직접 도구를 진화시킬 필요 없는 일회성 작업
- 코치가 계속 대신 Claude를 돌리는 구조이고 변경 의사 X
- 적용 범위·over-fit·검증 기준 이해 없이 단독 자력으로 넘기려는 상황
- LD가 사용할 AI 환경·실행 권한이 없어 단계 전환 자체가 불가능

**작은 루틴 AX 설계 (#30)**

- ROI상 완전 자동화보다 초안+수동 5분 복붙이 더 나을 수도 있다 (작은 루틴 AX).

## 패턴 11. Golden Case 검증

> **영역**: 5. 자동화 한계 인정 · **빈도**: ★★ · **흡수**: #19 Golden Case 검증

### 기본 분류
- 영역: 5. 자동화 한계 인정
- 패턴: 11. Golden Case 검증
- 실행 양식: Golden Case 기준 검증

### 한 줄 기준

수집 성공 로그만으로 핵심 데이터가 의미적으로 맞게 반영됐다고 보기 어려울 때 적용한다.

### 적용 신호

- 데이터가 여러 출처에서 들어온다.
- 화면에는 정상처럼 보이지만 실제 DB 반영이 틀릴 수 있다.
- 원천 데이터와 기대 반영 결과를 비교할 수 있다.
- 검증 가능한 대표 흐름 케이스와 회귀 방지 케이스를 만들 수 있다.

### 비적용 신호

- 원천 데이터와 기대 결과를 정의할 수 없다.
- 수집 성공 여부만 확인하면 충분한 단순 작업이다.
- 대표 흐름이나 회귀 방지 케이스를 만들 수 없다.
- 하나라도 실패했을 때 FAIL로 볼 기준을 합의하지 못했다.

### 필요한 입력값

- 원천 데이터 / 기대 반영 결과 / 대표 흐름 케이스 / 회귀 방지 케이스 / 실제 DB 조회 결과

### 판단 기준

- 데이터가 여러 출처에서 들어온다.
- 화면에는 정상처럼 보이지만 실제 DB 반영이 틀릴 수 있다.
- 검증 가능한 기준 케이스를 만들 수 있다.
- 하나라도 실패하면 데이터 반영 정확성은 FAIL로 보는 것이 맞다.

### 추천 액션

- 실행 시점: 구현물은 있으나 핵심 데이터 반영 정확성을 확인해야 할 때
- 실행 주체: 세션 담당자 또는 LD
- 액션 내용: 원천 데이터와 기대 결과가 명확한 대표 흐름 케이스와 회귀 방지 케이스 만듦. 실제 DB 조회 결과와 기대값 비교·실패 케이스 별도 남김
- 완료 기준: Golden Case 목록·실제 결과와 기대값 비교표·PASS/FAIL 판정 기준 정리

### 주의사항

- 오분류 위험: 수집 success 로그를 정확성 검증으로 착각 가능
- 헷갈리는 패턴: 수집·전달 5단계 점검(패턴 19) — Golden Case는 의미적으로 맞게 반영됐는지 검증, 5단계 점검은 병목 단계 찾음
- 쓰면 안 되는 조건: 원천과 기대 결과가 명확하지 않은 예시를 Golden Case로 쓰는 경우

왜 특정 규칙·스키마·제약을 넣었는지 나중에 사라질 위험이 있을 때 적용한다.

### 적용 신호

- 규칙이 임의로 보일 수 있다.
- 미래의 자신이나 AI가 맥락을 잊을 수 있다.
- 한 줄 요약보다 원문이 중요하다.
- 의사결정 발언·날짜·시각·발언자·원문이 있다.

### 비적용 신호

- 결정 근거가 아니라 일반 설명이나 잡담이다.
- 원문이 없어 의역만 남길 수 있다.
- 이미 문서 안에 출처와 이유가 충분히 남아 있다.
- 너무 많은 메모가 노이즈가 될 정도로 붙어 있다.

### 필요한 입력값

- 의사결정 발언 / 날짜·시각 / 발언자 / 원문 / 삽입 위치(`SKILL.md`·dictionary.md·schema·문서)

### 판단 기준

- 규칙이 임의로 보일 수 있다.
- 미래의 자신이나 AI가 맥락을 잊을 수 있다.
- 한 줄 요약보다 원문이 중요하다.
- 의역하면 근거 가치가 떨어진다.

### 추천 액션

- 실행 시점: 규칙·스키마·제약을 추가하거나 변경한 직후
- 실행 주체: 세션 담당자 또는 LD
- 액션 내용: `(YYYY-MM-DD HH:MM 발언자/출처): "원문"` 형태로 결정 근거를 `SKILL.md`·dictionary.md·schema·문서 안에 직접 삽입. 결정 근거 아닌 설명은 제외
- 완료 기준: 핵심 규칙·스키마·제약마다 원문 기반 근거 메모 붙고·불필요한 메모는 제외

### 주의사항

- 오분류 위험: 의역하면 근거 가치 떨어짐
- 헷갈리는 패턴: 단일 진실 원천+페인 컨펌(패턴 10) — 인라인 근거는 특정 결정의 출처를 남기는 것, 북극성은 전체 기능 판단 기준을 반복 고정
- 쓰면 안 되는 조건: 원문 없이 추정으로 발언 만들거나 의역하는 경우
- 추가 주의: 너무 많은 메모는 노이즈가 되므로 결정 근거에만 붙임

### 대표 사례

- 김동찬: "코치까지 권한 드리기 다소 불안해서요" 같은 발언을 근거로 권한·보안 원칙을 남김
- 손승완: P12 자막 분리 over-fit 같은 결정 근거를 시각·발언자·원문과 함께 남김

### 정보 부족 시 확인 질문

- 이 규칙이나 제약을 넣게 된 원문 발언이 있나요?
- 발언자와 날짜·시각을 확인할 수 있나요?
- 이 메모는 결정 근거인가요, 단순 설명인가요?
- 메모를 넣을 위치는 `SKILL.md`·schema·문서 중 어디인가요?
- 의역하지 않고 원문 그대로 남길 수 있나요?

## 패턴 16. 공통 컨텍스트 문서화

> **영역**: 7. 학습·구현 하네스 · **빈도**: ★ · **흡수**: #4 학습용 하네스 + #5 구현용 하네스

### 기본 분류
- 영역: 7. 학습·구현 하네스
- 패턴: 16. 공통 컨텍스트 문서화
- 실행 양식: (2 갈래) 학습용 하네스 작성 / 구현용 하네스 작성

### 한 줄 기준

LD와 AI가 같은 기준·판단으로 업무를 이해하도록 공통 문서를 두 시점에서 명시한다 — 형식지 미확정 시점(학습) / 도메인 판단 잡힌 후(구현).

### 적용 신호

**학습용 하네스 (#4)**
- 형식지가 없거나 부분적으로만 있다.
- LD와 AI가 같은 기준으로 업무를 이해하지 못한다.
- 도메인 규칙이 사람 머릿속에 흩어져 있다.
- AI가 바로 구현하면 방향을 잘못 잡을 가능성이 크다.
- LD가 "왜 이 구조인지" 아직 말로 설명하기 어렵다.

**구현용 하네스 (#5)**
- 학습용 하네스나 그에 준하는 공통 기준이 이미 있다.
- LD가 요구사항을 자기 말로 설명할 수 있다.
- 구현할 기능이 2~3개 정도로 명확하다.
- 데이터 연결 방식·파일 경계·합격 기준을 함께 묶어야 한다.
- 구현 전에 검증 기준을 먼저 잡아야 한다.

### 비적용 신호

**학습용 하네스 (#4)**
- 이미 입력값·판단 기준·출력 형식·합격 기준이 충분히 정리되어 있다
- LD가 요구사항과 구조의 존재 이유를 자기 말로 설명할 수 있다 (구현용 갈래에 가까움)
- 지금 필요한 것은 학습 문서가 아니라 구현 반복이나 테스트
- 시간이 없고 검증된 기존 하네스를 그대로 재사용할 수 있는 상태

**구현용 하네스 (#5)**
- 도메인 구조나 현실 로직이 아직 파악되지 않은 상태 (학습용 갈래가 먼저 필요)
- LD가 요구사항을 자기 말로 설명하지 못한다
- 입력 데이터·파일 경계·합격 기준이 아직 불명확하다
- 검증 기준 없이 AI에게 바로 구현을 맡기려는 상황

### 필요한 입력값

**학습용 하네스**: 세션 합의 / 문제 정의·범위·스택·보안·데이터 모델·사용자·빌드 순서 / 객체·관계·지표·도메인 구조 / 사람이 직접 확인할 예외 / 기존 사례·인라인 근거 메모
**구현용 하네스**: 학습용 하네스 결과 / LD가 원하는 기능 2~3개 / x·y·z 판단 / 파일 경계·데이터 연결 방식·합격 기준 / Plan v1·Validation·Plan v2 반복 기준

### 판단 기준

- LD가 "왜 이 구조인지" 설명하지 못하면 아직 구현보다 학습이 먼저다.
- LD가 요구사항을 자기 말로 설명할 수 있고 구현할 기능이 명확하고 검증 기준이 먼저 잡혀 있으면 구현용.

### 추천 액션

- 실행 시점: 구현 전 도메인 구조·판단 기준이 흩어져 있다고 판단된 직후(학습용) / 학습용 하네스로 도메인 판단 잡힌 뒤·실제 구현 기능 정해야 하는 시점(구현용)
- 실행 주체: 세션 담당자와 LD(학습용) / 세션 담당자·AI(구현용)
- 액션 내용:
  - **학습용 하네스**: 설계 원칙·객체·관계·지표·예외·보안·권한 제약·Q&A·시나리오 퀴즈를 하나의 학습용 하네스로 정리. LD가 각 구조 존재 이유를 설명할 수 있는지 확인
  - **구현용 하네스**: 구현할 기능·데이터 소스·파일 경계·합격 기준을 하나의 구현용 하네스로 묶음. 이후 Plan v1 → Validation → Plan v2 순서로 구현 계획·검증 기준 반복 정리
- 완료 기준:
  - **학습용 하네스**: LD 또는 코치가 주요 객체·관계·지표·규칙·예외의 존재 이유를 말로 설명할 수 있고, AI가 구현 전에 참고할 공통 기준 문서가 준비된다
  - **구현용 하네스**: 각 기능마다 사용자 스토리·데이터 연결 방식·합격 기준·구현 반복 종료 기준이 정리된다

### 주의사항

- 오분류 위험: 하네스를 문서 양으로만 이해하면 실제 판단 기준이 비어 있을 수 있음(학습용) / 현실 로직 파악·형식지화 없이 바로 구현용 하네스 쓰면 잘못된 자동화(구현용)

- 추가 주의: 하네스 목적은 AI와 LD가 같은 판단을 하게 만드는 것 / `/validated-plan` 같은 구현 반복 도구는 도메인 판단 잡힌 뒤 쓰는 것이 안전

### 대표 사례

- **학습용 하네스**: 김동찬 `docs/design-principles-v1.md` 10섹션·7개 객체·9개 관계·입과율·수료율 공식·무기명·PII·정책 변동 흡수 원칙 / 손승완 사전·정규식·Few-shot·LLM pass 도구 분담을 학습용 하네스로 만들고 over-fit 회피 퀴즈·시나리오 퀴즈 거침
- **구현용 하네스**: 김동찬 v1에서 데이터 연결과 스키마 학습 끝낸 뒤 v2에서 미해결 특이사항·폐강 위험 과정·확인 필요 정성 답변 3개 기능을 `/validated-plan`으로 구체화

- 어떤 자료를 넣고 어떤 기준으로 판단하고 어떤 결과가 나와야 하는지 문서로 정리되어 있나요?

## 패턴 18. DIKW 정보화

> **영역**: 8. 외부 표준 합성 · **빈도**: ★ · **흡수**: #16 DIKW 정보화

### 기본 분류
- 영역: 8. 외부 표준 합성
- 패턴: 18. DIKW 정보화
- 실행 양식: raw→시그널→점수 변환

### 한 줄 기준

raw 데이터는 많지만 의사결정 가능한 정보로 변환되지 않을 때 적용한다.

### 적용 신호

- 슬랙·메일·메모·시트·DB 같은 raw 데이터는 많다.
- 사용자가 데이터를 직접 보지만 판단 로직이 정리되지 않는다.
- Data → Information 변환이 끊겨 있다.
- 점수·시그널·카테고리로 바꾸면 판단 가능성이 생긴다.
- 결손 처리 기준이 필요하다.

### 비적용 신호

- raw가 이미 판단 가능한 시그널이나 점수로 변환되어 있다.
- 판단 질문이 없어 무엇을 정보화할지 정할 수 없다.
- 없는 데이터를 LLM 추정으로 메우려는 상황이다.
- 문제의 핵심이 정보 변환이 아니라 외부 표준과 현장 기준 합성이다.

### 필요한 입력값

- raw 데이터(슬랙·메일·메모·시트·DB) / 판단 질문 / 시그널 후보 / 결손 처리 기준 / 점수·티어 구조 후보

### 판단 기준

- Data → Information 변환이 끊겨 있다.
- 점수·시그널·카테고리로 바꾸면 판단 가능성이 생긴다.
- 없는 데이터를 만들어내면 안 된다.

### 추천 액션

- 실행 시점: raw는 있으나 의사결정에 바로 쓰이지 못하는 상황이 확인된 직후

- 완료 기준: raw→시그널 변환표·시그널→점수 매트릭스·점수→티어 구조·결손 처리 원칙 정리

### 주의사항

- 오분류 위험: 없는 데이터를 만들어내면 정보화가 아니라 추정

## 패턴 21. 검증 양식 4 갈래

> **영역**: 10. Validation 분기 · **빈도**: ★★★ · **흡수**: #21 1 Core + #22 2 Core + #23 비움 + #35 분모 fallback

### 기본 분류
- 영역: 10. Validation 분기
- 패턴: 21. 검증 양식 4 갈래
- 실행 양식: (4 갈래) 1 Core Validation 설계 / 2 Core Validation 설계 / Validation 비움 사유 기록 / 모수별 fallback 기준 설계

### 한 줄 기준

case별 *사용 = 결과* 직결 여부·검증 주인 유무·모수 충분도에 따라 Validation 양식을 분기한다.

### 적용 신호

**1 Core (#21)**: 도구 사용 자체가 산출물 생성으로 직결됨 / 사용 사이클·게시 완주·자발 실행 횟수 같은 직접 증거가 있음
**2 Core (#22)**: 도구 사용 후 별도 행동·효과가 이어져야 Y 해결 / 지속성·대응률·정확성·신뢰도 같은 두 축 필요 / 행동 기반 증거 확보 가능
**비움 (#23)**: 신청자와 실증자 다르고 지속 사용 주인 없음 / 대체 실증자 페인이 다른 도구 요구 / 도구 흡수 못 하는 LD 개인 운영 방식 큼 / 표준화 한계 명확
**분모 fallback (#35)**: 측정 기간 안에 사용 기회 자체 부족 가능 / 사용하지 않은 이유가 도구 문제인지 기회 부족인지 구분 필요 / 모수 0건 FAIL은 부당

### 비적용 신호

**1 Core Validation 설계 (#21)**
- 도구 실행만으로 Y 해결을 말할 수 없는 영역 (2 Core 갈래에 가까움)
- 사용 로그나 산출물 증거가 없어 1 Core 지표를 잡을 수 없다
- 결과물이 아니라 지속성·대응률·정확성 같은 별도 지표가 핵심
- 사용 후 별도 행동이나 운영 효과가 이어져야 하는 영역

**2 Core Validation 설계 (#22)**
- 도구 사용 자체가 곧 결과물 생성으로 끝나는 영역 (1 Core 갈래에 가까움)
- 사용 증거와 효과 증거를 분리할 수 없다
- 측정 기간이나 행동 결과를 확인할 자료가 없다
- 시간 감소율 같은 주관 회고만 있고 행동 기반 증거가 없는 상태

**Validation 비움 (#23)**
- 지속 검증 주인이 명확한 영역 (1 Core·2 Core 갈래에 가까움)
- 실제 활용 가능성이 있고 측정 가능한 Core가 있다
- 페인과 솔루션이 일치한다
- 도구 한계가 아니라 아직 검증 설계가 덜 된 상태 (검증 설계 보강이 먼저)

**분모 fallback (#35)**
- 측정 기간 안에 충분한 모수가 확보되는 영역 (1 Core·2 Core에 가까움)
- 사용 기회가 있었는데도 사용하지 않은 상황 (도구 문제로 봐야 함)
- 모수와 관계없이 동일 PASS/FAIL 기준을 적용해도 공정한 영역
- fallback을 *기준 완화*로 쓰려는 잘못된 의도가 있는 상황

### 필요한 입력값

**공통**: 측정 기간 / PASS/FAIL 기준
**1 Core**: 도구 실행 로그·산출물 / 사용 사이클 / 결과물 게시·완주 여부 / 자발적 실행 횟수
**2 Core**: 도구 사용 증거 / 행동·운영 결과 증거 / Core 1 후보 / Core 2 후보 / 참고 지표 후보
**비움**: 신청자와 실증자 관계 / 실제 활용 가능성 / 도구 한계 / 페인-니즈 일치 여부 / 본질적 한계
**분모 fallback**: 실제 사용 기회가 생기는 조건 / 예상 모수 / 사용 횟수 / 재사용 여부

### 판단 기준

- 사용하면 곧바로 산출물 나오면 1 Core / 사용 후 별도 효과 필요하면 2 Core.
- 지속 사용 주인 없거나 페인 mismatch 큼 → 비움 (비움은 실패가 아니라 정직한 판정).
- 측정 기간 안 모수 0~1건 가능 → fallback (모수별 PASS/FAIL/무판정 분기).
- 직결형 아닌데 1 Core만 보면 효과 과대평가 / 시간 감소율 같은 주관 회고만 Core 두면 위험.

### 추천 액션

- 실행 시점: case별 Validation 설계 단계 진입 시
- 실행 주체: 세션 담당자
- 액션 내용:
  - **1 Core**: 사용 사이클·결과물 게시·완주 여부·자발적 실행 횟수 중 1개를 Core로. 산출물·로그로 확인 가능한 PASS/FAIL 기준 붙임
  - **2 Core**: Core 1에 사용·지속성·배포 여부 / Core 2에 이슈 대응률·FP=0·정확성 같은 효과 지표. 시간 단축 체감·만족도·속도 분포는 참고 지표로 분리
  - **비움**: 비우는 사유·본질적 한계·다음 의사결정 갈래·회고 자산화 문서화. 왜 검증하지 않는지가 나중에 보이게
  - **분모 fallback**: 측정 기간·사용 기회 조건·예상 모수·사용 횟수·재사용 여부 정리. 모수 0건·1건·2건 이상별 PASS/FAIL/무판정 기준 따로 둠
- 완료 기준:
  - **1 Core**: 1개 Core 기준(사용 사이클·게시 완주·자발적 실행 횟수 중 1개)·증거 자료·PASS/FAIL 기준이 정리된다
  - **2 Core**: Core 1(사용·지속성·배포 여부)·Core 2(이슈 대응률·FP=0·정확성 같은 효과 지표)·참고 지표(시간 단축 체감·만족도·속도 분포)·측정 기간·PASS/FAIL 기준이 분리되어 정리된다
  - **비움**: Validation 비움 사유와 본질적 한계·다음 의사결정 갈래·회고 자산화가 문서화된다
  - **분모 fallback**: 모수 0건·1건·2건 이상별 PASS/FAIL/무판정 기준이 분리된 판정표·측정 유효성 확인 질문·사용·재사용 로그 기준이 정리된다

### 주의사항

- 오분류 위험: 직결형 아닌데 1 Core만 보면 효과 과대평가 / 시간 감소율만 Core로 두면 주관 회고에 과의존 / 비움 사유 없이 검증 비우면 실패 은폐처럼 보임 / fallback을 기준 완화로 쓰면 성과 판정 흐려짐
- 헷갈리는 패턴: 4 갈래끼리 — 1 Core는 사용 자체가 결과 / 2 Core는 사용과 효과 분리 / 비움은 검증 축 줄이는 게 아니라 검증하지 않는 이유 남김 / fallback은 검증 지표 자체가 아니라 모수 부족 상황의 판정 보정
- 쓰면 안 되는 조건: 사용 후 행동 변화·운영 효과가 별도로 필요한데 1 Core 적용 / 행동 기반 증거 없이 주관 체감만으로 PASS/FAIL / 측정 가능한 Core 있는데 편의상 검증 생략 / 모수 있는데 사용 안 한 경우와 모수 자체 없는 경우 섞음

### 대표 사례

- **2 Core**: 김동찬 루틴 지속성 21일 중 17일+이슈 대응률 70% / 손승완 도구 적용 모듈 비율 80%+FP=0 / 김민선 배포 여부+Golden Case 정확성 / 안유진B v2 실행 증거+위클리 회의 분석 활용 2회 이상
- **비움**: 이현진 운영일지 (강연정 실증·다른 페인·셀 색상·구두 합의·LD idiom 같은 결정론 도구 비흡수 영역 커서 의도적 비움)
- **분모 fallback**: 이수빈 커리큘럼 자동화 (5월 내 실제 제안 케이스 보고 제안 2건+ 2회 사용 PASS·제안 1건 1회 사용 PASS·제안 0건 무판정)

## 패턴 27. LLM 자기 평가

> **영역**: 10. Validation 분기 · **빈도**: ★★ · **출처**: DeepEval / arXiv 2506.13023 (260520 추가)

### 기본 분류

- 실행 양식: AI 평가자 기반 검증 설계

### 한 줄 기준

사람이 모든 산출물을 전수 검수하기 어렵고, 평가 기준을 rubric·PASS/FAIL 기준으로 명시할 수 있어 LLM을 보조 평가자로 써야 할 때 적용한다.

### 적용 신호

- AI 산출물이 많아 사람이 전수 검토하기 어렵다.
- 없는 내용 생성·질문 적합성·근거 충실도·관련성 같은 평가 기준을 문장으로 정의할 수 있다.
- 사람 판정 일부 또는 Golden Case와 비교해 평가자 LLM의 판정 품질을 확인할 수 있다.
- 반복 운영에서 검토 우선순위나 1차 PASS/FAIL 라벨이 필요하다.
- 산출물 자체 생성 LLM과 별도의 평가 프롬프트·평가 모델·평가 rubric을 둘 수 있다.

### 비적용 신호

- 평가 기준이 사람 취향·정치적 맥락·한국어 뉘앙스에 크게 의존하고 rubric으로 고정하기 어렵다.
- 사람 판정 샘플이나 Golden Case가 없어 평가자 LLM이 맞는지 비교할 수 없다.
- 최종 승인·고객 발송·법적 판단처럼 AI 판정을 그대로 확정값으로 쓰면 위험하다.
- 평가자 LLM과 피평가자 LLM이 같은 종류의 실수를 할 가능성이 큰데 교차 검증 장치가 없다.
- 산출물 수가 적어 사람이 직접 보는 편이 더 빠르고 안전하다.

### 필요한 입력값

- 평가 대상 산출물 / 평가 rubric / PASS·FAIL 또는 점수 기준 / 사람 판정 샘플 / Golden Case / 평가자 LLM 프롬프트 / 불일치 처리 기준

### 판단 기준

- 검증 대상은 패턴 21(검증 양식 4 갈래)로 먼저 정한다.
- LLM 자기 평가는 *무엇을 검증할지*가 아니라 *누가 판정할지*를 정하는 패턴이다.
- 평가 기준이 문장 rubric으로 명시되고, 사람 판정이나 Golden Case와 대조 가능해야 한다.
- 평가자 LLM은 최종 판정자가 아니라 검토 우선순위와 반복 운영 비용 절감용 보조 판정자다.

### 추천 액션

- 실행 시점: 검증 대상과 성공 기준은 정해졌지만 사람 전수 검수가 부담이 되는 때

- 액션 내용: 평가 rubric을 작성하고, 평가자 LLM 프롬프트·점수 기준·PASS/FAIL 기준·사람 재검토 조건을 정함. 최소 샘플에서 사람 판정과 LLM 판정을 비교하고 불일치 유형을 기록

### 주의사항

- 헷갈리는 패턴: 검증 양식 4 갈래(패턴 21) — 21은 검증 대상·범위 선택, LLM 자기 평가는 판정 주체 선택. Golden Case 검증(패턴 11) — Golden Case는 기준 사례 검증, LLM 자기 평가는 그 기준을 평가자 LLM이 적용하게 하는 방식
- 쓰면 안 되는 조건: 사람 판정 샘플 없이 평가자 LLM을 바로 신뢰하는 경우
- 추가 주의: self-preference·verbosity 편향, 같은 모델 계열의 공통 오류, 한국어 B2B 교육 도메인 신뢰도 미검증 가능성

### 대표 사례

- 1차 8 case 직접 적용 사례 없음
- 예상 적용: 만족도 자유응답 분류나 자막 교정 결과가 대량으로 쌓여 사람이 전수 확인하기 어려울 때, 사람 판정 샘플과 대조한 뒤 LLM 자기 평가를 1차 검토 우선순위 산정에 사용

- 사용자가 어떤 결과를 그대로 써도 되는지, 어디를 확인해야 하는지 구분하기 어렵다.
- 도구 출력물이 반복 사용되거나 다른 사람에게 전달되어 과신 위험이 있다.
- 정보 부족 시 확인 질문만으로는 부족하고, 최종 출력물 안에 메타 신호가 남아야 한다.
- 사람 검수·추가 질문·데이터 보강으로 넘길 조건을 명시할 수 있다.

### 비적용 신호

- 정량 계산·고정 변환처럼 코드로 결정 가능하고 불확실성 표시가 필요 없다.
- 근거 데이터가 없는데도 AI가 확신도를 숫자로 만들도록 요구한다.
- 낮은 확신도일 때 사람이 무엇을 해야 하는지 후속 액션이 없다.
- 사용자에게 보여줄 출력물이 아니라 내부 실험용 응답이다.
- 확신도 표시가 실제 검증 없이 PASS/FAIL처럼 쓰일 위험이 크다.

### 필요한 입력값

- AI 출력 항목 / 사용자가 믿어도 되는 기준 / 정보 부족 기준 / 추정 포함 기준 / 사람 확인 필요 조건 / 메타 신호 라벨 / 낮은 신호 이후 후속 액션

### 판단 기준

- AI 자기 확신도는 정답 근거가 아니라 검수 행동을 유도하는 신호다.
- `확신함`보다 `근거 부족`, `정보 부족`, `추정 포함`, `사람 확인 필요`처럼 행동으로 이어지는 라벨이 안전하다.
- 낮은 신호가 떴을 때 사람이 확인할 자료·질문·다음 단계가 함께 있어야 한다.
- 정보 결손은 LLM 추정으로 메우지 않고 결손으로 표시한다.

### 추천 액션

- 실행 시점: AI 출력물을 사용자가 그대로 복붙·공유·업무 반영할 가능성이 보이는 때
- 실행 주체: 세션 담당자와 LD
- 액션 내용: 출력 항목 옆에 붙일 메타 신호 라벨을 정의하고, 각 라벨별 후속 액션을 정함. 낮은 신뢰 신호가 뜬 항목은 사람 확인·추가 질문·데이터 보강으로 넘기는 규칙을 작성
- 완료 기준: 메타 신호 라벨표·신호별 후속 액션·사람 확인 조건·출력 예시가 정리된다

### 주의사항

- 오분류 위험: AI가 "확신함"이라고 표시한 답도 틀릴 수 있음
- 헷갈리는 패턴: Stage·HITL 도구 분담(패턴 1) — HITL은 사람 개입 위치 설계, AI 자기 한계 신호는 출력물 안에 사람 확인 필요 신호를 남기는 설계. DIKW 정보화(패턴 18) — DIKW는 raw 데이터를 정보로 바꾸는 양식, 본 패턴은 AI 판단의 불확실성을 표시하는 양식
- 쓰면 안 되는 조건: 확신도 숫자를 정확도처럼 쓰려는 경우
- 추가 주의: calibration 검증 전에는 AI 자기 확신도를 검증 기준으로 쓰지 않는다

### 대표 사례

- 1차 8 case 직접 적용 사례 없음
- 예상 적용: 강사 피드백 메일 초안, 고객 리드 기여 추정, 커리큘럼 개선 제안처럼 AI가 근거 부족 상태에서 일부 추론할 수 있는 산출물에 `추정 포함`, `사람 확인 필요` 라벨을 붙임

### 정보 부족 시 확인 질문

- 낮은 신호가 뜨면 사용자는 무엇을 확인해야 하나요?

## 패턴 29. 프롬프트 반복 개선

> **영역**: 1. AI 역할 축소 · **빈도**: ★★ · **출처**: IBM Research arXiv 2403.08950 (260520 추가)

### 기본 분류
- 영역: 1. AI 역할 축소
- 패턴: 29. 프롬프트 반복 개선
- 실행 양식: 프롬프트·추론 설정 반복 조정

### 한 줄 기준

AI 결과가 원하는 기준에 조금씩 어긋나고, 프롬프트·모델·출력 길이·반복 회피 같은 입력 지시와 설정값을 작은 단위로 바꿔가며 품질을 개선해야 할 때 적용한다.

### 적용 신호

- 첫 프롬프트 결과가 방향은 맞지만 톤·구조·정확성·누락·반복 표현에서 어긋난다.
- 문제의 핵심이 데이터 부족보다 지시 방식·출력 형식·예시 부족에 있다.
- 프롬프트 변경 전후 결과를 비교할 샘플이나 기대 출력이 있다.
- 모델 선택, max tokens, 답변 길이, 반복 표현 회피 정도 같은 inference 설정도 함께 흔들리고 있다.
- 큰 재설계보다 작은 프롬프트 수정과 비교를 여러 번 반복하는 편이 적합하다.

### 비적용 신호

- 프롬프트 문제가 아니라 입력 데이터·업무 기준·정답 정의 자체가 비어 있다.
- 결과 불안정의 원인이 정량 계산 재현성이라 코드화가 먼저 필요하다.
- 출력 형식은 맞지만 사람 암묵지 룰이 빠져 있어 diff 룰 발견이 먼저 필요하다.
- 변경 전후를 비교할 기준 샘플이 없다.
- 매번 큰 프롬프트를 새로 쓰고 있어 어떤 변경이 효과를 냈는지 추적할 수 없다.

### 필요한 입력값

- 현재 프롬프트 / 목표 출력 / 실패한 출력 예시 / 기대 출력 예시 / 변경할 변수 목록 / 모델·출력 길이·반복 회피 설정 / 변경 로그

### 판단 기준

- 프롬프트 반복 개선은 출력 차이를 룰로 번역하는 것이 아니라, 입력 지시 방식 자체를 조정하는 문제다.
- 한 번에 여러 변수를 바꾸면 효과 원인을 알 수 없으므로 작은 변경 단위로 반복한다.
- 프롬프트 변경은 샘플 출력 비교와 함께 기록되어야 한다.
- 반복 개선 뒤에는 잠금 버전과 재사용 조건을 남겨야 한다.

### 추천 액션

- 실행 시점: AI 출력이 대체로 맞지만 계속 같은 유형의 어긋남이 반복될 때
- 실행 주체: 세션 담당자와 LD
- 액션 내용: 현재 프롬프트와 실패 출력 예시를 기준선으로 저장. 역할·맥락·예시·제약·출력 형식·모델 설정 중 하나씩만 바꿔 결과를 비교하고, 효과 있는 변경만 잠금 버전에 반영
- 완료 기준: 기준선 프롬프트·변경 로그·비교 출력·잠금 프롬프트·재사용 조건이 정리된다

### 주의사항

- 오분류 위험: 데이터나 판단 기준이 비어 있는데 프롬프트만 고치면 겉보기만 좋아짐
- 헷갈리는 패턴: AI 초안·정답 차이 분류(패턴 14) — 패턴 14는 출력 차이에서 사람 암묵지를 룰로 뽑는 문제, 프롬프트 반복 개선은 입력 지시와 설정값을 조정하는 문제. 타이트·넓음 동시 점검(패턴 25) — 룰 폭 문제와 프롬프트 표현 문제를 구분해야 함

## 패턴 30. LLM 동적 도구 호출

> **영역**: 1. AI 역할 축소 · **빈도**: ★★ · **출처**: arXiv 2412.01130·2508.02979·2509.18076 / Microsoft Tech Community (260520 추가)

### 기본 분류
- 영역: 1. AI 역할 축소
- 패턴: 30. LLM 동적 도구 호출
- 실행 양식: 상황별 도구 선택·호출 설계

### 한 줄 기준

고정된 AI 처리 chain만으로는 부족하고, 입력 상황에 따라 LLM이 검색·계산·DB 조회·파일 읽기 같은 도구를 골라 호출해야 할 때 적용한다.

### 적용 신호

- 같은 요청이라도 입력 상태에 따라 필요한 도구가 달라진다.
- 검색, 계산, DB 조회, 파일 읽기, 캘린더·시트·슬랙 조회 같은 외부 도구가 여러 개 있다.
- 미리 1단계→2단계→3단계 고정 chain으로 설계하면 예외가 너무 많다.
- LLM이 생각→도구 호출→관찰→다시 판단하는 loop가 필요하다.
- 여러 도구 호출 결과를 종합해야 최종 답이나 액션이 나온다.

### 비적용 신호

- 항상 같은 순서의 수집→분석→출력으로 충분하다.
- 도구가 1개뿐이거나 사람이 직접 호출해도 부담이 작다.
- 권한·인증·로그·실패 복구 설계가 없다.
- 잘못된 도구 호출이 고객 발송, 예약, 결제, 삭제 같은 되돌리기 어려운 액션으로 이어진다.
- LLM이 도구를 선택할 기준을 문서화할 수 없다.

### 필요한 입력값

- 사용 가능한 도구 목록 / 도구별 입력·출력 / 권한 범위 / 도구 선택 기준 / 호출 실패 시 fallback / 로그 형식 / 사람 확인이 필요한 액션 목록

### 판단 기준

- 고정 chain으로 충분하면 패턴 6(AI 처리 chain 분담)을 우선 적용한다.
- 입력마다 필요한 도구가 달라질 때만 동적 Tool Use를 검토한다.
- LLM이 도구를 고르는 기준, 호출 결과를 해석하는 기준, 실패 시 멈추는 기준이 필요하다.
- 되돌리기 어려운 액션은 사람 확인 단계를 둔다.

### 추천 액션

- 실행 시점: 여러 도구가 필요하지만 호출 순서와 필요 여부가 입력마다 달라지는 것을 확인한 때
- 실행 주체: 세션 담당자와 LD
- 액션 내용: 도구 목록과 권한 범위를 정리하고, 도구 선택 기준·호출 입력·반환값·실패 fallback을 표로 작성. 위험 액션은 HITL 조건을 붙이고, 모든 호출 로그를 남기는 구조를 설계
- 완료 기준: 도구 카탈로그·선택 기준·호출 계약·실패 fallback·사람 확인 조건·로그 형식이 정리된다

### 주의사항

- 오분류 위험: 고정 chain으로 충분한 업무에 동적 호출을 넣으면 디버깅과 권한 관리만 어려워짐
- 헷갈리는 패턴: AI 처리 chain 분담(패턴 6) — chain 분담은 미리 정한 순서대로 실행, LLM 동적 도구 호출은 LLM이 상황에 따라 도구를 선택. Stage·HITL 도구 분담(패턴 1) — LLM 동적 도구 호출은 도구 호출 선택 자체가 핵심
- 쓰면 안 되는 조건: 권한·실패 복구·호출 로그 없이 LLM에게 도구 사용 권한만 주는 경우
- 추가 주의: 예약·발송·삭제·결제처럼 외부 상태가 바뀌는 액션은 사람 확인이나 되돌리기 경로가 필요하다

### 대표 사례

- 1차 8 case 직접 적용 사례 없음. 이수빈 커리큘럼 자동화의 14~15개 chain은 고정 chain이라 본 패턴과 다름
- 예상 적용: 회의실 예약, 다중 시스템 조회, 조건별 자동 처리, 대화형 에이전트처럼 입력마다 필요한 도구가 달라지는 세션

### 정보 부족 시 확인 질문

- 사용 가능한 도구는 무엇인가요?
- 요청마다 필요한 도구가 달라지나요, 아니면 항상 같은 순서인가요?
- 각 도구의 입력값과 반환값은 무엇인가요?
- 도구 호출 실패 시 어떻게 멈추거나 우회하나요?
- 사람 확인 없이 실행하면 위험한 도구 호출은 무엇인가요?
