## 패턴 10. 단일 진실 원천 + 페인 컨펌

> **영역**: 4. 본질 anchor · **빈도**: ★ · **흡수**: #13 단일 진실 원천/북극성 + #14 페인 재정의 3회 컨펌

### 기본 분류
- 영역: 4. 본질 anchor
- 패턴: 10. 단일 진실 원천 + 페인 컨펌
- 실행 양식: (2 갈래) 북극성 문장 고정 / 페인 재정의 컨펌

### 한 줄 기준

페인·솔루션 anchor가 흔들릴 위험을 두 시점에서 잡는다 — 개발 중 흔들림 방지(고정) / 시연 후 해결감 없을 때 재정의.

### 적용 신호

**북극성 문장 고정 (#13)**
- 페인이 흔들린 적이 있다 / 신청자가 말한 니즈와 실제 페인이 달랐다.
- 개발자가 기능 구현 중 본질을 잊기 쉽다.
- README·코드 주석·설치 가이드·`SKILL.md` 등 반복 삽입 위치가 있다.

**페인 재정의 컨펌 (#14)**
- 기술적으로 완성됐지만 사용자가 납득하지 못한다.
- 사전 신청 페인이 실제 페인이 아니었을 수 있다.
- 니즈와 페인이 섞여 있다 / 본부장·파트장·코치 피드백으로 페인 재확인 필요.

### 비적용 신호

**북극성 문장 고정 (#13)**
- 페인이 한 번도 흔들린 적이 없고 솔루션 판단도 한결같다
- 반복 삽입할 위치(README·주석·`SKILL.md` 등)가 없거나 문장을 넣을 자리가 마땅치 않다
- 페인 자체가 흔들리고 있어 *고정*보다 *재정의*가 먼저 필요한 상태 (페인 재정의 갈래에 가까움)
- 단순 슬로건만 만들고 실제 기능 판단에 반영할 위치가 없다

**페인 재정의 컨펌 (#14)**
- 시연 결과 사용자가 페인 해결감을 명확히 느낀다
- 페인이 이미 명확히 정해져 있고 *고정*만 필요한 상태 (북극성 갈래에 가까움)
- 사용자 반응·피드백 자료 없이 추정만으로 페인을 바꾸려는 상황
- 문제 원인이 페인 정의가 아니라 구현 버그·데이터 반영 오류로 확인됨

### 필요한 입력값

**북극성 문장 고정**: 페인 one sentence / 솔루션 one sentence / 반복 삽입 위치(README·코드 주석·설치 가이드·`SKILL.md`) / 기능 판단에 사용할 질문
**페인 재정의 컨펌**: 초기 페인 가설 / 시연 결과·사용자 반응 / 본부장·파트장·코치 피드백 / 니즈와 페인 후보

### 판단 기준

- 북극성은 슬로건이 아니라 기능 판단 기준이어야 한다.
- "이 기능이 북극성과 맞는가?"를 물을 수 있어야 한다.
- 페인이 틀렸다면 북극성을 고집하지 말고 재정의해야 한다.
- 니즈는 솔루션 후보일 수 있지만 페인 자체가 아니다.
- 페인 재정의 전에는 구현을 멈추는 것이 맞다.

### 추천 액션

- 실행 시점: 구현 중 기능이 늘거나 페인-솔루션이 흔들릴 때(북극성) / 시연 후 페인 해결감이 없거나 사용자가 납득하지 못한 직후(페인 재정의)
- 실행 주체: 세션 담당자와 LD
- 액션 내용:
  - **북극성 문장 고정**: 페인 one sentence·솔루션 one sentence 정함. README·코드 주석·설치 가이드·`SKILL.md` 등 반복 위치에 같은 문장 넣음. 새 기능마다 "북극성과 맞는가?" 확인
  - **페인 재정의 컨펌**: 초기 페인 가설·시연 반응·피드백을 놓고 self-clarify·사고 사다리·대면+슬랙 컨펌 순서로 페인 다시 작성. 마지막에 자각 페인과 잠재 페인 구분
- 완료 기준:
  - **북극성 문장 고정**: 북극성 문장·반복 삽입 위치·기능 판단 질문이 정리된다
  - **페인 재정의 컨펌**: 최종 페인 one sentence와 자각 페인·잠재 페인 구분이 합의된다

### 주의사항

- 오분류 위험: 북극성을 슬로건으로만 쓰면 기능 판단 기준이 안 됨 / 페인이 틀렸는데 구현 계속하면 완성도가 높아져도 안 쓰임
- 헷갈리는 패턴: 두 갈래끼리 — 북극성은 확정된 페인을 반복 고정, 페인 재정의는 페인 자체가 틀렸을 때 다시 잡음
- 쓰면 안 되는 조건: 페인 자체가 틀렸거나 사용자가 납득하지 못한 상태에서 북극성만 박는 경우 / 사용자 반응·피드백 없이 추정만으로 페인 바꾸는 경우

### 대표 사례

- **북극성 문장 고정**: 이현진 운영일지 (두 페인 one sentence를 README·코드 주석·설치 가이드에 반복 반영) / 이현진 딜판단 ("딜 데이터를 가치있는 정보로 바꾸지 못해 판단 로직이 정리되지 않은 것"을 설계 매커니즘으로 반영)
- **페인 재정의 컨펌**: 이현진 운영일지·딜판단 (1차 플러그인은 E2E로 완성됐지만 시연에서 페인 해결감 X·이후 운영 페인과 딜 페인 한 문장씩 재정의·두 플러그인 분리)

### 정보 부족 시 확인 질문

- 이 도구가 해결해야 하는 페인을 한 문장으로 말할 수 있나요? 솔루션도 한 문장으로 말할 수 있나요?
- 이 문장을 README·코드 주석·설치 가이드·`SKILL.md` 중 어디에 반복해서 넣을 수 있나요?
- 시연 후 사용자가 페인 해결감을 느꼈나요?
- 사용자가 말한 것은 페인인가요, 원하는 솔루션인가요?
- 지금 페인 자체가 맞는지 다시 확인해야 하는 신호가 있나요?
