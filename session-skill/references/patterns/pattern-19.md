## 패턴 19. 수집·전달 5단계 점검

> **영역**: 9. 데이터 흐름 점검 · **빈도**: ★ · **흡수**: #8 데이터 흐름 5단계 점검

### 기본 분류
- 영역: 9. 데이터 흐름 점검
- 패턴: 19. 수집·전달 5단계 점검
- 실행 양식: 데이터 흐름 5단계 대조

### 한 줄 기준

최종 화면에서 문제를 발견했지만 원인이 가져오기·정리·저장·반영·결과 중 어디인지 모를 때 적용한다.

### 적용 신호

- 최종 화면 숫자가 원본이나 기대값과 다르다.
- 수집 성공 로그는 있지만 원하는 데이터가 다 들어왔는지 확신하기 어렵다.
- 문제를 도구 이름으로 부르고 있지만 실제 원인은 흐름 중간에 있을 수 있다.
- 같은 기간·범위·중복 기준으로 세고 있는지 확인해야 한다.

### 비적용 신호

- 원본부터 최종 화면까지 단계별 수량이 이미 일치한다.
- 문제 원인이 특정 코드 오류나 권한 문제로 이미 확정되어 있다.
- 최종 화면 문제가 아니라 새 데이터 소스를 DB에 쌓을지 결정하는 상황이다.
- 단계별 수량을 확인할 원본이나 저장 결과가 없다.

### 필요한 입력값

- 원본 수 / 정리 후 수 / 저장된 수 / 화면 반영 수 / 최종 화면 숫자 / 마지막 성공 시각 / 처리 범위

### 판단 기준

- "success" 로그는 원하는 데이터가 다 들어왔다는 뜻이 아니다.
- 도구 이름으로 문제를 부르지 말고 흐름 단계로 다시 부른다.
- 같은 기간·범위·중복 기준으로 세고 있는지 확인.
- 병목 단계가 확인되기 전에는 전체 재수집부터 하지 않는다.

### 추천 액션

- 실행 시점: 최종 화면 숫자나 반영 결과가 이상하지만 원인 단계가 불명확할 때
- 실행 주체: 세션 담당자 또는 LD
- 액션 내용: 가져오기·정리·저장·반영·결과 5단계별 수량과 마지막 성공 시각을 같은 범위 기준으로 적음. 수량이 처음 어긋나는 단계를 병목으로 표시·재처리 범위를 하루·한 출처·한 사용자·샘플 몇 건 중 하나로 좁힘
- 완료 기준: 단계별 수량 대조표·병목 단계·최소 재처리 범위 정리

### 주의사항

- 오분류 위험: 전체 재수집·전체 재적재부터 하면 더 큰 운영 사고 가능
- 헷갈리는 패턴: 데이터 소스 결정 3단(패턴 20) — 5단계 점검은 이미 흐르는 데이터의 병목 찾음, 데이터 소스 결정은 새 데이터 소스의 적재 방식 결정
- 쓰면 안 되는 조건: 단계별 원본·수량을 확인할 수 없는 상태에서 추정으로 병목을 단정하는 경우
- 추가 주의: 운영 메모·임시 문장·실제 업무 데이터·제외값을 구분

### 대표 사례

- 김민선: 강사 대시보드에서 Gmail이 적게 들어온다·Slack이 느리다·Drive·시트가 안 잡힌다·화면 숫자가 다르다 같은 증상을 도구 오류가 아니라 데이터 흐름 문제로 재해석

### 정보 부족 시 확인 질문

- 원본에는 몇 건이 있어야 하나요?
- 정리 후·저장 후·화면 반영 후 숫자를 각각 확인할 수 있나요?
- 지금 비교하는 기간과 범위가 단계마다 같나요?
- 마지막으로 성공한 시각은 언제인가요?
- 전체 재처리 전에 샘플 몇 건이나 한 출처만 좁혀서 확인할 수 있나요?
