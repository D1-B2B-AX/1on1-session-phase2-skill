## 패턴 25. 타이트·넓음 동시 점검

> **영역**: 14. 룰 폭 균형 · **빈도**: ★ · **흡수**: #37 spec·룰 타이트 vs 넓음 균형

### 기본 분류
- 영역: 14. 룰 폭 균형
- 패턴: 25. 타이트·넓음 동시 점검
- 실행 양식: 룰 폭 조정 기준 설계

### 한 줄 기준

규칙을 너무 빡빡하게 잡으면 본질과 충돌하고, 너무 넓게 잡으면 결함이 통과할 때 적용한다.

### 적용 신호

- 규칙이 너무 빡빡해 정상 사례까지 막고 있다.
- 규칙이 너무 넓어 결함이 통과하고 있다.
- 본질 기준과 실행 규칙이 충돌하고 있다.
- 강제 조건을 줄이거나 늘렸을 때 부작용이 생긴다.
- spec 정정과 재검증이 필요하다.

### 비적용 신호

- 규칙 폭 문제가 아니라 입력값·판단 기준 자체가 비어 있다.
- 현재 규칙이 정상 사례와 결함을 충분히 잘 구분한다.
- 발생한 결함이나 막힌 정상 사례를 확인할 수 없다.
- 규칙 수정 뒤 재검증할 기준이 없다.

### 필요한 입력값

- 현재 규칙·spec / 강제 조건 / 통과해야 하는 게이트 / 발생한 결함 / 규칙 때문에 막힌 정상 사례

### 판단 기준

- 규칙이 너무 빡빡해 정상 사례까지 막고 있는가?
- 규칙이 너무 넓어 결함이 통과하고 있는가?
- 본질 기준과 실행 규칙이 충돌하고 있는가?
- 강제 조건을 줄이거나 늘렸을 때 어떤 부작용이 생기는가?

### 추천 액션

- 실행 시점: spec·룰을 적용한 뒤 정상 사례 차단이나 결함 통과가 확인된 때
- 실행 주체: 세션 담당자와 LD
- 액션 내용: 현재 규칙·너무 빡빡한 규칙·너무 넓은 규칙·본질과 충돌하는 지점을 표로 나눔. 수정안에는 기존 정상 사례가 깨지지 않는지 확인할 재검증 기준 붙임
- 완료 기준: 룰 폭 문제 표·수정안·기존 정상 사례와 결함 케이스 재검증 기준 정리

### 주의사항

- 오분류 위험: 결함 하나를 막으려고 전체 산출물 품질을 떨어뜨릴 수 있음
- 헷갈리는 패턴: Fresh 검증(패턴 12) — Fresh 검증은 룰의 일반화 안전성 보는 것, 룰 폭 균형은 타이트함과 넓음의 부작용 조정. 또 프롬프트 반복 개선(패턴 29) — 룰 폭 균형은 룰의 타이트함·넓음 부작용 조정 영역·프롬프트 반복 개선은 입력 지시 방식과 설정값 자체를 조정하는 양식
- 쓰면 안 되는 조건: 발생한 결함이나 막힌 정상 사례 없이 감으로 룰을 고치는 경우
- 추가 주의: 규칙 수정 뒤에는 기존 정상 사례가 깨지지 않는지도 확인

### 대표 사례

- 이수빈 커리큘럼 자동화: spec에 강제 조건·게이트·룰을 박을 때, 너무 타이트하면 커리큘럼 원형의 본질과 충돌하고 너무 넓으면 결함이 통과. 후속 cycle에서 spec 정정·재검증 필요

### 정보 부족 시 확인 질문

- 현재 규칙이 정상 사례까지 막고 있나요?
- 현재 규칙이 너무 넓어 결함을 통과시키고 있나요?
- 본질 기준과 실행 규칙이 충돌하는 지점은 어디인가요?
- 규칙을 고치면 어떤 기존 정상 사례가 깨질 수 있나요?
- 수정 뒤 어떤 케이스로 재검증하나요?
