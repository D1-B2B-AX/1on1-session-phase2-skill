## 패턴 24. plan 단위 분할 검토

> **영역**: 13. 계획 검토 분산 · **빈도**: ★ · **흡수**: #36 validated-plan 검토 부담 분산

### 기본 분류
- 영역: 13. 계획 검토 분산
- 패턴: 24. plan 단위 분할 검토
- 실행 양식: 계획 검토 분담 설계

### 한 줄 기준

계획 규모나 복잡도가 커서 한 사람이 한 번에 정합성을 검토하기 어려울 때 적용한다.

### 적용 신호

- 계획이 너무 커서 한 사람이 전체 정합성을 보기 어렵다.
- 여러 공정이 연결되어 있어 앞 단계 오류가 뒤 단계로 전파된다.
- 다른 검증자나 다른 세션의 관점이 들어오면 결함을 더 빨리 찾을 수 있다.
- 자동 검증만으로 본문 품질이나 구조 정합을 보장하기 어렵다.

### 비적용 신호

- 계획 규모가 작아 한 사람이 정합성을 충분히 볼 수 있다.
- 공정 간 연결이 약해 오류 전파 위험이 작다.
- 누가 어떤 기준으로 검토할지 나눌 수 없다.
- 검토자를 늘려도 중복 검토만 늘어날 상황이다.

### 필요한 입력값

- 큰 규모의 계획 문서 / 기능·공정별 하위 계획 / 검토해야 할 기준 / 검증자·다른 세션의 관점 / 발견된 결함 목록

### 판단 기준

- 계획이 너무 커서 한 사람이 전체 정합성을 보기 어려운가?
- 여러 공정이 연결되어 있어 앞 단계 오류가 뒤 단계로 전파되는가?
- 다른 검증자·다른 세션의 관점이 들어오면 결함을 더 빨리 찾을 수 있는가?
- 자동 검증만으로 본문 품질이나 구조 정합을 보장하기 어려운가?

### 추천 액션

- 실행 시점: 큰 계획이나 여러 공정 계획을 검토해야 하는 단계
- 실행 주체: 세션 담당자와 검증자
- 액션 내용: 계획을 기능·공정별로 나눔·각 검토자가 볼 기준 정함. 결함 발견 목록·수정 후 재검토 기준·다음 case에서 비교할 미확정 질문 남김
- 완료 기준: 검토 분담표·공정별 확인 기준·결함 목록·수정 후 재검토 기준 정리

### 주의사항

- 오분류 위험: 검토자를 늘린다고 자동으로 품질이 좋아지는 것은 아님
- 헷갈리는 패턴: AI 처리 chain 분담(패턴 6) — 검토 부담 분산은 계획 검토 역할을 나누는 것, LLM chain은 실행 단계의 입력·출력 계약
- 쓰면 안 되는 조건: 누가 어떤 기준으로 검토할지 나누지 않은 경우
- 추가 주의: 자동 검증 게이트 통과와 본문 정합성은 별개

### 대표 사례

- 이수빈 커리큘럼 자동화: 전체 plan과 후속 공정이 커지면서 한 사람이 한 번에 검토하기 어려운 부담. 본 case에서는 간이 plan 방식 자체의 한계인지·spec 설계 결함인지·case 복잡도 때문인지가 미확정으로 남아 다음 case 비교 필요

### 정보 부족 시 확인 질문

- 계획이 한 사람이 한 번에 보기 어려울 만큼 큰가요?
- 어떤 공정이 앞뒤로 연결되어 있나요?
- 앞 단계 오류가 뒤 단계로 전파될 위험이 있나요?
- 누가 어떤 기준으로 검토할지 나눌 수 있나요?
- 자동 검증을 통과해도 사람이 봐야 할 본문 정합성은 무엇인가요?
