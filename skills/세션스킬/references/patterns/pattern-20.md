## 패턴 20. 데이터 소스 결정 3단

> **영역**: 9. 데이터 흐름 점검 · **빈도**: ★ · **흡수**: #9 데이터 가르마 3단 질문

### 기본 분류
- 영역: 9. 데이터 흐름 점검
- 패턴: 20. 데이터 소스 결정 3단
- 실행 양식: DB/API 판정

### 한 줄 기준

새 데이터 소스를 DB에 쌓을지 API로 그대로 볼지 결정해야 할 때 적용한다.

### 적용 신호

- 새 데이터 소스가 있다.
- 여러 소스와 합쳐야 하는지 결정해야 한다.
- 시간 흐름 비교가 필요한지 판단해야 한다.
- 여러 화면에서 반복 재사용하는지 판단해야 한다.
- DB에 쌓을지 API로 직접 볼지 결정이 필요하다.

### 비적용 신호

- 이미 DB/API 방식이 정해져 있고 문제는 흐름 단계의 병목이다.
- 데이터 소스가 하나뿐이고 지금 상태만 보면 된다.
- 개인정보나 동기화 리스크 때문에 원본 그대로 봐야 하는 조건이 명확하다.
- 데이터 연결보다 판단 기준이나 출력물 설계가 먼저 필요한 상황이다.

### 필요한 입력값

- 데이터 소스 목록 / 조합 필요 여부 / 시간 흐름 비교 필요 여부 / 여러 화면 재사용 여부 / 개인정보 또는 저장 회피 조건

### 판단 기준

- 여러 소스와 합쳐야 하면 DB로 본다.
- 시간 흐름 비교가 필요하면 DB로 본다.
- 여러 화면에서 반복 재사용하면 DB로 본다.
- 모두 아니면 API 직접 조회로 둔다.

### 추천 액션

- 실행 시점: 새 데이터 소스를 도구에 연결하기 전
- 실행 주체: 세션 담당자와 LD
- 액션 내용: 데이터 소스별로 "여러 소스와 합치는가 / 시간 흐름 비교가 필요한가 / 여러 화면에서 재사용하는가" 질문·하나라도 예면 DB·모두 아니면 API 직접 조회로 판정. 저장 회피가 필요한 예외는 별도 표시
- 완료 기준: 모든 데이터 소스에 DB/API 판정과 이유·예외 조건 정리

### 주의사항

- 오분류 위험: 원본 그대로 볼 데이터까지 DB화하면 개인정보·동기화 리스크 커짐
- 헷갈리는 패턴: 수집·전달 5단계 점검(패턴 19) — 데이터 소스 결정은 적재 방식 결정, 5단계 점검은 이미 만든 흐름의 병목 확인
- 쓰면 안 되는 조건: DB에 쌓은 뒤 생기는 운영 책임을 검토하지 않은 경우
- 추가 주의: DB에 쌓으면 운영 책임도 생김

### 대표 사례

- 김동찬: 통합 시트·출석부·시험·설문은 DB 적재로 판정. 메타 시트처럼 조합이 필요 없고 지금 상태만 보는 것은 API 직접. 정성 답변 원본은 PII 저장 회피 때문에 API 직접

### 정보 부족 시 확인 질문

- 이 데이터는 다른 소스와 합쳐야 하나요?
- 이 데이터는 시간 흐름 비교가 필요한가요?
- 이 데이터는 여러 화면에서 반복 재사용되나요?
- 원본 그대로만 봐야 하는 개인정보나 저장 회피 조건이 있나요?
- DB에 쌓았을 때 누가 동기화와 운영 책임을 지나요?
